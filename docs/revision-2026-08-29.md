**Qué puede hacer alguien con esto, sin tocar la app:**

- Con la contraseña de Neon: conectarse directo a la base de producción por internet y leer, editar
  o borrar las ~3.100 personas con nombre, correo, teléfono e ingreso declarado. Neon es público:

- Con el `AUTH_SECRET` de producción: **firmar un JWT de sesión propio** con `rol: "gerente"` y

  `lib/auth/config.ts:11`), así que el secreto de firma **es** la autenticación. No hace falta una
  cuenta de Google ni estar en la tabla `users`.
- Con los códigos de recuperación de Vercel: tomarse la cuenta que controla el despliegue y todas

1. **Rotar todo, asumiendo compromiso.** No hace falta averiguar cuál sigue viva; rotar es más
   barato que verificar.
   - Vercel: regenerar los códigos de recuperación y revisar sesiones y tokens activos.
   - Neon: *Reset password* del rol `neondb_owner` en la rama `production`. Sin revelar la
     contraseña en pantalla.
   - `AUTH_SECRET`: generar uno nuevo para producción y otro para local. Se cierran todas las
     sesiones, que es exactamente lo que se quiere.
   - Google Cloud: nuevo secreto de cliente OAuth, y borrar el anterior.
   - Composio: revocar la API key y emitir otra.
   - Cuenta de servicio: como el ID de la llave quedó expuesto, rotarla también (`npm run cuenta-servicio`).
2. **Revisar accesos antes de rotar**, para saber si alguien entró: logs de conexión de Neon
   (Monitoring), *Recent activity* de la cuenta de Google, log de auditoría de Vercel.
3. **Sacar los PNG del historial**, no solo del árbol. Un `git rm` deja el blob en cada commit
   anterior. Con [`git-filter-repo`](https://github.com/newren/git-filter-repo):

   ```bash
   git filter-repo --invert-paths --path-glob '*.png' --force
   ```

   Después `git push --force` y avisar a quien tenga un clon para que vuelva a clonar. Ojo: GitHub
   guarda los blobs huérfanos un tiempo, así que **la rotación del punto 1 es la que realmente
   cierra el hueco**, no la limpieza del historial.
4. **Que no vuelva a pasar.** Tres barreras baratas, en orden de efectividad:
   - `.gitignore`: agregar `*.png` y `*.jpg` en la raíz (`public/` sigue permitido con `!public/**`).
   - Activar **GitHub Secret Scanning con Push Protection** en el repo (Settings → Code security).
     No detecta secretos dentro de imágenes, pero sí los de texto, y es gratis.
   - Un hook `pre-commit` que rechace el commit si aparece un archivo binario nuevo en la raíz.
5. **Regla de trabajo**, que es la raíz de todo esto: nunca capturar la pantalla completa mientras
   hay un secreto visible. Si hay que documentar un paso, capturar solo la ventana (`⌘⇧4` y luego
   barra espaciadora) y guardarla fuera de la carpeta del repo.

## S-02 — ALTO — Desactivar un usuario no lo saca de la app hasta 30 días después

**Dónde:** `lib/auth/index.ts:36`

```ts
if (user || trigger === "update" || !token.rol) {
  const registro = await buscarUsuario(email);
  ...
}
```

La consulta a la base solo corre en tres casos: al iniciar sesión (`user`), cuando alguien llama
explícitamente a `update()`, o si el token no trae rol. **En una petición normal no corre.**
Y nadie en la app llama a `update()`: `useSession` no se usa en ningún componente.

Sumado a que no hay `maxAge` configurado en ningún lado (verificado: no aparece en `lib/`, `app/`,
`next.config.ts` ni `proxy.ts`), la sesión dura lo que dura el default de Auth.js: **30 días**.

Consecuencia: `npm run usuarios -- quitar <correo>` marca `activo = false` y no pasa nada. La
persona sigue entrando, con su rol, durante hasta un mes. Lo mismo si a un gerente lo bajan a
closer: sigue viendo el comparativo entre closers, la caja y la pauta. `PROJECT.md` regla 6 dice
que eso es política de la empresa, no preferencia de UI.

El propio código lo sabe. `scripts/usuarios.ts:90` imprime *"queda inactivo. No podrá entrar en la
próxima emisión de token"*. Pero `STATE.md` afirma lo contrario: *"revalida rol contra la DB al
iniciar sesión y en `update`, y vacía el token si el usuario fue desactivado ... así revocar a
alguien surte efecto sin esperar a que expire el JWT"*. La segunda mitad de esa frase no es cierta
(ver [B-02](#b-02--la-documentación-afirma-cosas-que-el-código-no-hace)).

**Arreglo.** Dos opciones, de menor a mayor esfuerzo:

- **Revalidar en cada emisión de token.** Quitar la condición y consultar siempre. Es una consulta
  por índice único sobre una tabla de menos de diez filas, y el callback `jwt` no corre en cada
  request sino cuando se refresca el token. Es la opción correcta para el tamaño de este equipo.
- Si más adelante el costo importa: agregar `sessionVersion int` a `users`, meterlo en el token,
  compararlo en el callback `session` e incrementarlo al desactivar o cambiar de rol. Revocación
  inmediata sin consultar la base en cada refresco.

En ambos casos, bajar `session.maxAge` a algo razonable (8 horas de jornada, o 7 días con
`updateAge`) y **corregir la frase de `STATE.md`**.

## S-03 — ALTO — El rol cae a `"closer"` por defecto en vez de fallar cerrado

**Dónde:** `lib/auth/config.ts:18-24`

```ts
session({ session, token }) {
  if (session.user) {
    session.user.id = token.usuarioId ?? "";
    session.user.rol = esRolValido(token.rol) ? token.rol : "closer";
    session.user.closerId = token.closerId ?? null;
  }
  return session;
}
```

Cuando el callback `jwt` vacía el token de un usuario desactivado (`lib/auth/index.ts:40`), deja
`usuarioId: undefined` y `rol: undefined`. Acá eso se traduce a `id: ""` y **`rol: "closer"`**.

Hoy no se explota, porque `""` es falsy y tanto `proxy.ts:26` como `requireSession()` cortan por
`session.user.id`. Es decir: **la app está segura por el `id`, no por el rol.** El rol ya viajó
adulterado dentro de la sesión.

Es frágil por dos razones concretas. Primera: cualquier código futuro que decida sobre
`session.user.rol` sin verificar antes el `id` trata a un token vacío como un closer legítimo.
Segunda: contradice la decisión de diseño que el propio repo defiende y testea, la de que no hay
herencia de roles y que un rol ausente no es un rol menor (`tests/roles.test.ts:16`,
*"sin rol no pasa nada"*).

**Arreglo.** Que el callback falle cerrado: si `token.usuarioId` o `token.rol` no son válidos,
devolver la sesión sin `user` en vez de rellenar con un rol inventado. Y agregar el test que hoy
falta: un token vacío no produce una sesión con rol.

## S-04 — MEDIO — `POST /api/sync/[programa]` devuelve al navegador el mensaje de error interno

**Dónde:** `app/api/sync/[programa]/route.ts:24-30`

```ts
} catch (error) {
  if (error instanceof Error && !("status" in error)) {
    return Response.json({ error: error.message }, { status: 422 });
  }
  return respuestaDeError(error);
}
```

La intención era buena: que un `MapeoInvalidoError` llegue completo a la pantalla para poder
arreglar el mapeo sin abrir logs. Pero la condición no filtra por tipo de error, filtra por
"no tiene `status`". Con eso, **cualquier** excepción interna sale al cliente: un error del driver
de Neon (que suele traer host y endpoint), uno de `googleapis` (que trae el `spreadsheetId` y a
veces fragmentos de la petición), o un `TypeError` con su mensaje.

Está detrás de `requireRole("gerente")`, así que el impacto es acotado. Pero rompe la razón de ser
de `respuestaDeError`, que existe justamente para que los errores no controlados salgan como
`"Error interno."` y solo se registren en el servidor (`lib/auth/guards.ts:46-47`).

**Arreglo.** Filtrar por tipo, no por forma:

```ts
} catch (error) {
  if (error instanceof MapeoInvalidoError) {
    return Response.json({ error: error.message }, { status: 422 });
  }
  return respuestaDeError(error);
}
```

## S-05 — MEDIO — La app no manda ninguna cabecera de seguridad

**Dónde:** `next.config.ts` está vacío (verificado: no hay `headers()` en ningún lado).

Falta todo: `Content-Security-Policy`, `Strict-Transport-Security`, `X-Frame-Options` /
`frame-ancestors`, `Referrer-Policy`, `X-Content-Type-Options`, `Permissions-Policy`.

Para una app que muestra datos personales de miles de leads, las dos que más pesan son:

- **Sin `frame-ancestors`**, cualquier sitio puede meter `retia-metrics.vercel.app` en un iframe
  invisible y hacer clickjacking sobre un gerente con sesión abierta. En la Fase 4, cuando haya
  botones que escriben de vuelta en Sheets, eso deja de ser teórico.
- **Sin CSP**, cualquier XSS futuro (una dependencia comprometida, un `dangerouslySetInnerHTML` que
  entre en la Fase 5 con los PDFs) tiene vía libre para exfiltrar la sesión.

**Arreglo.** Un bloque `headers()` en `next.config.ts`. Empezar por `frame-ancestors 'none'`,
`Strict-Transport-Security`, `Referrer-Policy: strict-origin-when-cross-origin` y
`X-Content-Type-Options: nosniff`, que no rompen nada. La CSP completa conviene montarla con nonce
cuando se agregue Recharts en la Fase 2, para no tener que aflojarla después.

## S-06 — MEDIO — La PII queda duplicada en dos lugares sin control de acceso ni retención

**Dónde:** `lib/db/schema.ts:147` y `lib/db/schema.ts:266-282`

Dos sitios guardan datos personales además de las columnas tipadas de `people`:

- `people.raw` (jsonb) guarda **la fila completa del formulario**, tal como vino de la hoja. Incluye
  las columnas que el mapeo no usa.
- `change_log.valorAnterior` / `valorNuevo` son `text` plano. Cuando cambia `telefono`,
  `ingresoDeclarado` o `porQueAplico`, el valor viejo y el nuevo quedan escritos ahí, con el nombre
  de la persona en `etiqueta`.

Hoy no hay ningún endpoint que los lea, así que no hay exposición activa. Pero el "panel de cambios"
está en el alcance de la Fase 2, y ahí hay que responder tres preguntas que conviene decidir ahora
y no cuando la pantalla ya esté hecha:

1. **Quién lo ve.** `PROJECT.md` regla 6 dice que un closer no ve datos de otros. La bitácora, tal
   como está, no tiene noción de a qué closer pertenece cada persona.
2. **Qué campos merecen bitácora.** Que cambie el `estado` o el `numAplicaciones` es señal
   operativa. Que cambie el teléfono es un dato personal más guardado una vez más.
3. **Cuánto se guarda.** Hoy nada purga `change_log` ni `people.raw`. Si mañana alguien ejerce
   derecho de supresión, hay que borrarlo de tres lugares y nadie lo tiene escrito.

**Arreglo.** Definir la lista de campos que van a la bitácora (recomendación: los de estado y
conteo, no los de contacto), guardar en `raw` solo las claves que el mapeo **no** cubre, y agregar
una política de retención con un job de purga. Es media hora ahora y evita una migración con datos
sensibles después.

## S-07 — MEDIO — El cron compara el secreto sin tiempo constante y devuelve errores crudos sin sesión

**Dónde:** `app/api/cron/sync/route.ts:22` y `:35`

```ts
if (enviado !== `Bearer ${esperado}`) { ... }       // línea 22
fallos.push({ programa: p.slug, error: e instanceof Error ? e.message : String(e) });  // línea 35
```

Dos cosas, ambas menores por separado:

- La comparación con `!==` corta en el primer byte distinto. Por red es poco práctico de explotar,
  así que esto es endurecimiento, no un agujero.
- La línea 35 sí importa más: esta ruta está en la lista de rutas públicas de `proxy.ts:22` y el
  cuerpo de la respuesta incluye `e.message` de `sincronizarPersonas`. Ese mensaje puede ser un
  `MapeoInvalidoError`, que por diseño **imprime todos los encabezados reales de la hoja**
  (`lib/sheets/mapeo.ts:32-34`). Los encabezados son las preguntas del formulario de aplicación.
  Solo se llega ahí con el secreto correcto, pero es información de negocio saliendo por una ruta
  sin sesión.

**Arreglo.** `crypto.timingSafeEqual` sobre buffers de igual longitud para la comparación, y que la
respuesta del cron devuelva conteos (`{ ok, sincronizados: 2, fallos: 1 }`) dejando el detalle en
`sync_runs.errores`, que ya existe para eso.

## S-08 — MEDIO — Los scripts pasan secretos por línea de comandos a `python3`

**Dónde:** `scripts/rotar-secretos.sh:48` y `scripts/cargar-cuenta-servicio.sh:45`

```bash
python3 - "$ARCHIVO" "$nuevo" "$nuevo_auth_secret" <<'PY'
python3 - "$ARCHIVO" "$B64" <<'PY'
```

Los argumentos de un proceso son visibles en la tabla de procesos: cualquier usuario del equipo
puede hacer `ps aux` mientras el script corre y leerlos. El segundo caso es el peor: pasa **la
llave privada completa de la cuenta de servicio** en base64 como argumento.

Es un riesgo local, no remoto, y el equipo trabaja en máquinas personales. Pero el resto de estos
scripts está escrito con cuidado real (lectura sin eco, `umask 077`, `chmod 600`, borrar el JSON de
Descargas), así que este es el único eslabón flojo de una cadena que por lo demás está bien hecha.

**Arreglo.** Pasarlos por stdin o por variable de entorno del proceso hijo:

```bash
NUEVO="$nuevo" SESION="$nuevo_auth_secret" python3 - "$ARCHIVO" <<'PY'
import os, re, sys
google, sesion = os.environ["NUEVO"], os.environ["SESION"]
PY
```

## S-09 — MEDIO — Los respaldos `.env.local.bak-*` quedan en claro para siempre

**Dónde:** `scripts/configurar-env.sh:92`, `scripts/rotar-secretos.sh:43`,
`scripts/cargar-cuenta-servicio.sh:43`

Los tres scripts copian `.env.local` a `.env.local.bak-<fecha>` antes de escribir, y ninguno lo
borra después. El `.gitignore` los cubre (`.env*` los alcanza), así que no llegan a git. Pero se
acumulan en el disco, en texto plano, con los secretos **viejos y nuevos**.

Esto vacía de sentido la rotación: si el archivo con la contraseña anterior sigue ahí, rotar solo
sirve contra quien vio la pantalla, no contra quien tiene acceso al disco. `STATE.md` menciona que
los respaldos del 18 de agosto se borraron a mano, lo cual confirma que el problema se conoce pero
que la solución fue manual y de una sola vez.

**Arreglo.** Que cada script deje como máximo un respaldo, con `chmod 600`, y borre los anteriores.
Agregar `npm run limpiar-respaldos` para pasarlos por `rm -P` (sobrescritura) y correrlo al final
de cada rotación.

## S-10 — BAJO — `trustHost: true` sin `AUTH_URL` fijado

**Dónde:** `lib/auth/config.ts:27`

Con `trustHost: true`, Auth.js construye las URLs de callback a partir de la cabecera `Host` de la
petición. En Vercel hace falta y es lo normal, pero deja la puerta abierta a que un alias de
preview o una cabecera `X-Forwarded-Host` manipulada dirijan el flujo. `.env.example` ya tiene la
línea `AUTH_URL` comentada.

**Arreglo.** Descomentarla y fijar `AUTH_URL=https://retia-metrics.vercel.app` en las variables de
producción de Vercel.

## S-11 — BAJO — El redirect abierto en `/login?desde=` está tapado por accidente, no por diseño

**Dónde:** `app/login/page.tsx:23` y `:47`

```ts
const desde = typeof params.desde === "string" ? params.desde : undefined;
...
await signIn("google", { redirectTo: desde ?? "/" });
```

`desde` viaja desde la query string hasta `redirectTo` sin ninguna validación. **Hoy no es
explotable**, porque el callback `redirect` por defecto de Auth.js descarta cualquier URL que no
sea del mismo origen, y el repo no define un callback `redirect` propio.

Lo señalo igual porque la protección es invisible: no está escrita en ningún lado, y el día que
alguien agregue un callback `redirect` personalizado (algo que suele hacerse para manejar el
`callbackUrl`), el redirect abierto aparece sin que nadie toque esta línea. Un usuario de Retia
recibe un link a `retia-metrics.vercel.app/login?desde=...`, ve el dominio correcto, inicia sesión
y termina en un sitio ajeno.

**Arreglo.** Una línea que hace la garantía explícita:

```ts
const destino = desde?.startsWith("/") && !desde.startsWith("//") ? desde : "/";
```

## S-12 — BAJO — Los route handlers no tienen CSRF propio; dependen de `SameSite=Lax`

**Dónde:** `app/api/sync/[programa]/route.ts` y `components/boton-sincronizar.tsx:17`

`POST /api/sync/:programa` cambia estado y no lleva token CSRF. Los Route Handlers de Next, a
diferencia de las Server Actions, no traen protección incorporada. Hoy alcanza con que la cookie de
sesión de Auth.js sea `SameSite=Lax`, que bloquea el POST cross-site.

Depender de una sola capa del navegador para un endpoint que escribe está bien mientras lo único
que hace es disparar un sync. En la Fase 4, cuando el registro de llamadas escriba de vuelta en
Sheets (`PROJECT.md` regla 7), conviene que las mutaciones sean **Server Actions** en vez de route
handlers: Next les pone la verificación de origen sola y el problema desaparece.

**Esto bloquea la Fase 2.** El primer paso de esa fase no es escribir el motor de métricas, es

2. Agregar `estado` a `CAMPOS_COMPARABLES` para que los cambios de etapa queden en la bitácora.

3. Decidir si `capacidadInvertir` se guarda (hay que agregarle columna) o se saca del mapeo.
   Que esté mapeado y no se use confunde a quien lea el código.
4. Un test que fije la regla: si la hoja trae `estado`, la persona insertada no queda en el default.

## F-02 — ALTO — Una fila sin fecha válida se trata como la más reciente y pisa datos buenos

**Dónde:** `lib/sheets/dedup.ts:112-119`

```ts
const esMasReciente =
  !fecha || !existente.fechaUltimaAplicacion || fecha >= existente.fechaUltimaAplicacion;

for (const c of CAMPOS_TEXTO) {
  const v = limpiar(fila[c]);
  if (v === null) continue;
  if (existente[c] === null || esMasReciente) existente[c] = v;
}
```

El `!fecha` inicial dice: si esta fila **no tiene fecha parseable, considerala la más reciente**.
Con lo cual sus valores sobrescriben los de la aplicación buena anterior.

Es fácil que pase. `parsearFecha` (`lib/sheets/mapeo.ts:102-125`) solo entiende dos formatos:
`d/m/yyyy` con hora opcional, e ISO. Devuelve `null` para una celda vacía, para un número de serie
de Sheets, para `19 ago 2026` y para cualquier otra redacción. Como `fechaAplicacion` es obligatoria
solo a nivel de **columna** (`OBLIGATORIOS_FORMULARIO`), no de **valor**, una fila con la celda
vacía pasa el filtro y entra por esta rama.

Con 2.965 filas y 38% de duplicados en Tactical Investor, alcanza con que un puñado tenga la fecha
en blanco para corromper el teléfono o el cargo de esas personas en silencio. La bitácora lo va a
registrar como un cambio legítimo del sync.

El test más cercano (`tests/dedup.test.ts:125`, *"una aplicación posterior con campos vacíos no
borra lo que ya se sabía"*) cubre el caso del **campo** vacío, no el de la **fecha** vacía.

**Arreglo.** Invertir el default: sin fecha, la fila solo rellena huecos, nunca sobrescribe.

```ts
const esMasReciente =
  fecha != null &&
  (existente.fechaUltimaAplicacion == null || fecha >= existente.fechaUltimaAplicacion);
```

Y agregar el test que falta: una fila sin fecha con un teléfono distinto no cambia el teléfono ya
conocido.

## F-03 — ALTO — Dos sincronizaciones simultáneas revientan y dejan la base a medias

**Dónde:** `lib/sheets/sync.ts:162-164`

```ts
for (let i = 0; i < aInsertar.length; i += 200) {
  await db.insert(people).values(aInsertar.slice(i, i + 200));
}
```

Un `insert` pelado, sin `onConflictDoUpdate`, contra una tabla con índice único
`(program_id, email_normalizado)`. Nada impide que dos sincronizaciones se solapen:

- el cron corre cada 15 minutos (`vercel.json`),
- `maxDuration` es 300 segundos, o sea que una corrida puede durar hasta 5 minutos,
- y el botón "Sincronizar ahora" de `/ajustes/fuentes` dispara otra en cualquier momento.

Si dos corridas leen la hoja antes de que la primera termine de insertar, las dos calculan el mismo
conjunto de "nuevas". La segunda choca contra el índice único, el lote entero lanza y la corrida se
aborta a mitad de escritura.

Y no hay transacción que lo salve: el driver `neon-http` no soporta transacciones de varias
sentencias, así que cuando eso pasa ya se actualizó `sources.ultimaSync` (línea 104) y ya entraron
algunos lotes de personas. Queda un estado intermedio que nadie limpia.

**Arreglo.** Dos piezas, las dos necesarias:

1. **Idempotencia real en la escritura.** Cambiar el insert por un upsert:

   ```ts
   await db.insert(people).values(lote)
     .onConflictDoUpdate({
       target: [people.programId, people.emailNormalizado],
       set: { /* campos del sync */, updatedAt: new Date() },
     });
   ```

   Además de resolver la carrera, esto habilita el arreglo de [F-04](#f-04--medio--las-actualizaciones-van-de-a-una-la-próxima-carga-grande-se-pasa-del-límite).

2. **Un solo sync a la vez por programa.** Un `pg_advisory_lock` con el `programId` como llave, o
   la versión simple: antes de arrancar, verificar que no haya un `sync_runs` en estado `corriendo`
   para ese programa (con un timeout que descarte corridas colgadas) y salir con "ya hay una
   sincronización en curso".

## F-04 — MEDIO — Las actualizaciones van de a una: la próxima carga grande se pasa del límite

**Dónde:** `lib/sheets/sync.ts:142-145`

```ts
await db
  .update(people)
  .set({ ...aRegistro(p, programId), updatedAt: new Date() })
  .where(eq(people.id, previo.id));
```

Un `UPDATE` por persona modificada, dentro del bucle, y cada uno es un viaje HTTP independiente a
Neon (`neon-http`).

Esto ya se aprendió una vez en este mismo archivo: `STATE.md` cuenta que insertar fila por fila
tardaba 161 segundos y que por eso se pasó a lotes de 200. **El camino de actualización tiene la
misma forma y no se arregló.** Hoy no se nota porque en régimen cambian pocas personas por corrida.

Se nota el día que cambie algo transversal: se corrige el mapeo (que es exactamente lo que hay que
hacer para [F-01](#f-01--alto--el-sync-lee-estado-de-la-hoja-y-lo-tira-el-embudo-no-tiene-datos)),
se renombra una columna en la hoja, o se agrega un campo al mapeo. Ahí las ~3.100 personas
aparecen con diff y son ~3.100 viajes secuenciales. A ~50 ms cada uno son más de dos minutos; a
100 ms se pasa de los 300 segundos de `maxDuration` y el cron muere sin terminar.

**Arreglo.** El mismo upsert por lotes de [F-03](#f-03--alto--dos-sincronizaciones-simultáneas-revientan-y-dejan-la-base-a-medias)
resuelve inserciones y actualizaciones en la misma sentencia. El cálculo de diffs para la bitácora
se puede seguir haciendo en memoria antes de escribir, que es donde ya está.

## F-05 — MEDIO — Las fechas se guardan en la zona horaria del servidor

**Dónde:** `lib/sheets/mapeo.ts:109-115`

```ts
const f = new Date(
  Number(a), Number(mes) - 1, Number(d),
  Number(h), Number(min), Number(seg),
);
```

Este constructor interpreta los componentes en la **zona horaria local del proceso**. En el equipo
de Michael eso es `America/Bogota` (UTC-5). En una función de Vercel es **UTC**. La columna destino
es `timestamptz`.

O sea: la misma fila de la misma hoja produce dos instantes distintos según dónde corra el sync.
Una aplicación de las 7:30 p.m. del 12 de agosto queda como `2026-08-13T00:30:00Z` si la sincronizó
Michael desde su máquina, y como `2026-08-12T19:30:00Z` si la sincronizó el cron. Cinco horas de
diferencia, y para las filas cercanas a medianoche, **un día hábil de diferencia**.

Hay un agravante silencioso: `CAMPOS_COMPARABLES` no incluye las fechas, así que si una persona ya
existe y lo único que difiere es el instante, `compararCampos` devuelve cero diffs, no se actualiza
y no queda registro. El resultado es una tabla donde cada persona tiene la zona horaria de quien la
insertó primero, sin ninguna señal de que eso pasó.

Impacta directo en la Fase 2: `PROJECT.md` regla 3 dice que solo cuentan los días hábiles, y "ritmo
por día hábil" es una de las métricas centrales. Con las fechas mezcladas, los leads de la franja
nocturna caen del lado equivocado.

**Arreglo.** Construir el instante fijando el desplazamiento de forma explícita, no dejándoselo al
entorno:

```ts
// Colombia no tiene horario de verano: el desplazamiento es -05:00 siempre.
const f = new Date(`${a}-${mes.padStart(2,"0")}-${d.padStart(2,"0")}T${hh}:${mm}:${ss}-05:00`);
```

Antes de cambiarlo, verificar qué zona asumieron las filas ya guardadas y decidir si se re-sincroniza
desde cero (que es barato: la carga en frío tarda 4 segundos según `STATE.md`).

# 3. Buenas prácticas y arquitectura

## B-01 — ALTO — El motor de sincronización, que es lo más riesgoso, no tiene tests

Los tests que hay están bien elegidos y cubren lo correcto: la lógica pura de roles, las guardas
sobre los route handlers reales, el dedup y los permisos del sync. Pero
**`sincronizarPersonas()` no tiene ni un test**, y es la única función del proyecto que escribe en
la base.

Los tres hallazgos altos de la sección anterior ([F-02](#f-02--alto--una-fila-sin-fecha-válida-se-trata-como-la-más-reciente-y-pisa-datos-buenos),
[F-03](#f-03--alto--dos-sincronizaciones-simultáneas-revientan-y-dejan-la-base-a-medias),
[F-04](#f-04--medio--las-actualizaciones-van-de-a-una-la-próxima-carga-grande-se-pasa-del-límite))
viven ahí, y los tres son de los que un test agarra a la primera.

**Arreglo.** El problema es que la función mezcla decisión con entrada/salida. Separarla en dos:

- una función pura `planificarSync(personasDeHoja, personasEnBase) → { aInsertar, aActualizar, cambios }`,
  que se testea sin base de datos igual que `deduplicarPorCorreo`;
- y un envoltorio delgado que lee, llama a la anterior y escribe.

Con eso, los casos "fila sin fecha no pisa", "sync sin novedades no escribe nada" y "un campo que
cambia genera exactamente una fila de bitácora" pasan a ser tests de tres líneas. El repo ya
demostró que sabe hacer esto: `dedup.ts` está separado de `sync.ts` justo por esta razón.

## B-02 — La documentación afirma cosas que el código no hace

`AGENTS.md` establece el flujo de trabajo: leer `PROJECT.md` + `STATE.md` + el spec de la fase, y

fuente de verdad de la próxima sesión, así que una afirmación falsa ahí no se corrige: se hereda.

Tres desajustes concretos:

| "`lib/sheets/` y `lib/metrics/` están vacías (Fase 1 y Fase 2)" | `lib/sheets/` tiene cinco archivos y es el corazón de la Fase 1. Línea vieja que quedó |
| "**Tests** — 33 pasando" y, más abajo, "11 tests de Vitest pasando" | Dos números distintos en el mismo documento |

**Arreglo.** Agregar al checklist de cierre de fase un paso explícito: releer `STATE.md` completo y

## B-03 — `zod` está instalado y no se usa en ninguna parte

Está en `dependencies` (`zod@^4.4.3`) y no lo importa ningún archivo (verificado sobre `lib/`,
`app/`, `components/`, `scripts/` y `types/`).

Hoy no hay entrada de usuario que validar: el único parámetro es `programa`, que va a un `eq()`
parametrizado de Drizzle y no permite inyección. Pero la Fase 4 recibe el formulario de registro de
llamadas, que es un POST con cuerpo, y la Fase 5 recibe archivos subidos.

**Arreglo.** Fijar el patrón ahora, con el endpoint que ya existe: un esquema por ruta, parseado en
el borde, y el error de validación traducido a 400 por `respuestaDeError`. Cuesta veinte minutos
ahora y evita que la Fase 4 invente su propia forma de validar.

## B-04 — Cada handler inventa su propio manejo de errores

`lib/auth/guards.ts` define `respuestaDeError`, y `app/api/admin/ping/route.ts` la usa tal cual: es
el patrón de referencia y está bien pensado (traduce los errores tipados, registra el resto en el
servidor y devuelve `"Error interno."`).

Pero de los cuatro endpoints con lógica, dos se salen: `/api/sync/[programa]` inventa su rama de
422 ([S-04](#s-04--medio--post-apisyncprograma-devuelve-al-navegador-el-mensaje-de-error-interno))
y `/api/cron/sync` arma sus respuestas a mano. Con cuatro endpoints la inconsistencia se maneja
leyendo los cuatro; con veinte, no.

**Arreglo.** Que `respuestaDeError` conozca también `MapeoInvalidoError` (→ 422) y los errores de
zod (→ 400), y que **todos** los handlers terminen en ella. Un solo lugar donde decidir qué sale al
cliente.

## B-05 — El cliente de la base se crea al importar el módulo y lanza si falta la variable

**Dónde:** `lib/db/index.ts:5-13`

```ts
const connectionString = process.env.DATABASE_URL;
if (!connectionString) throw new Error("Falta DATABASE_URL...");
export const db = drizzle(neon(connectionString), { schema });
```

Fallar ruidosamente es la decisión correcta. Fallar **en tiempo de importación** es lo que genera
el problema: cualquier archivo que importe `lib/db`, aunque sea para un tipo, revienta si no hay
variable. Por eso `scripts/load-env.ts` tiene que ser el primer import de todos los scripts, y por
eso hay un párrafo en `STATE.md` explicándolo.

Es un requisito de orden de imports sostenido por convención y documentación. Funciona hasta que
alguien agrega un import arriba sin saber.

**Arreglo.** Inicialización perezosa: un getter que cree el cliente la primera vez que se usa y
lance ahí. El error sigue siendo ruidoso y llega en el mismo momento en que importa (al primer
query), pero desaparece la restricción de orden y `load-env.ts` deja de ser obligatorio en la
primera línea.

## B-06 — `people.raw` guarda la fila completa y crece sin techo

**Dónde:** `lib/db/schema.ts:147`

Se guarda la fila entera del formulario por persona. Con ~3.100 personas no es un problema de
tamaño (la base va en 31 MB según la consola de Neon). Sí lo es de propósito: duplica lo que ya
está en columnas tipadas, agrega el ángulo de privacidad de

El comentario dice "para auditar sin volver a Sheets", que es un buen motivo. Si ese es el motivo,
lo que hace falta guardar es lo que **no** está en las columnas tipadas.

**Arreglo.** Guardar en `raw` solo las claves que el mapeo no cubre. Se conserva la capacidad de
auditar y se deja de duplicar datos personales.

## B-07 — `set -uo pipefail` sin `-e` en los tres scripts de shell

**Dónde:** `configurar-env.sh:4`, `rotar-secretos.sh:4`, `cargar-cuenta-servicio.sh:4`

Sin `-e`, un comando que falla no detiene el script. El caso concreto:
`cargar-cuenta-servicio.sh:43` hace `cp "$ARCHIVO" "${ARCHIVO}.bak-..."` sin verificar que
`.env.local` exista. Si no existe, `cp` falla, el script sigue, y python revienta después con un
error mucho menos claro que "no existe .env.local".

**Arreglo.** `set -euo pipefail`, y donde un fallo sea aceptable, marcarlo con `|| true`.

## B-08 — `re.sub` con reemplazo sin escapar

**Dónde:** `scripts/rotar-secretos.sh:52-53`

```python
s = re.sub(r'^AUTH_GOOGLE_SECRET=.*$', f'AUTH_GOOGLE_SECRET="{google}"', s, flags=re.M)
```

El string de reemplazo de `re.sub` interpreta secuencias con backslash (`\1`, `\g<1>`, `\n`). Los
secretos actuales son base64 y `GOCSPX-`, que no traen backslashes, así que hoy funciona.

Lo anoto porque el modo de fallar es feo: si alguna vez un secreto trae un backslash, el archivo se
escribe con el valor mutilado, sin ningún error, y lo que se ve después es un fallo de
autenticación sin pista de por qué.

**Arreglo.** Usar una función como reemplazo, que no interpreta nada:

```python
s = re.sub(r'^AUTH_GOOGLE_SECRET=.*$', lambda _: f'AUTH_GOOGLE_SECRET="{google}"', s, flags=re.M)
```
